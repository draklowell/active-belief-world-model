# Notebook conventions

Research notebooks use Jupyter and are saved as `.ipynb` files in this folder. Use `NN_name.ipynb` for new notebooks and preserve existing filenames. See `00_jupyter_example.ipynb` for an interactive example using IPython display and `ipywidgets`.

1. **A notebook is a draft and a narrative, not the source of truth.** Working code that's used more than once belongs in `src/`, and the notebook imports it — the rule of thumb is: if a function is needed twice, it belongs in `src/`, not copy-pasted between notebooks.
2. **Every notebook opens with a markdown cell**: Goal, Input, Conclusion. The Conclusion is written **after** the analysis, once you know what the results actually say — not drafted in advance and left unchanged.
3. **Check execution requirements before rerunning.** Inspect code and metadata for hardware, data, dependencies, side effects, and runtime. Prefer an existing configured remote kernel with the required environment when available; use a local kernel only for verified lightweight CPU notebooks. Do not automatically rerun GPU, model training or fine-tuning, or other expensive notebooks, locally or remotely. These runs require explicit user authorization and suitable compute. When execution is appropriate, use `Restart & Run All` on the selected kernel. If suitable compute is unavailable, requirements are unclear, or execution is not authorized, validate notebook schema and code syntax without executing cells. Preserve saved outputs and report that execution was not run, why it was skipped, and which outputs may be stale.
4. **Outputs are committed.** This course's convention is to keep cell outputs in the `.ipynb` file (not strip them), so plots and tables are visible directly on GitHub without anyone having to re-run the notebook first. The tradeoff is merge conflicts (see rule 5) and file size — keep figures reasonably sized, don't `df.head(10000)` into a cell.
5. **Notebooks and git merges don't mix well.** The underlying JSON makes conflicts nearly unreadable, and git can't meaningfully merge two people's changes to the same notebook. Practical rule: one notebook, one author, at a time. If two people need to work on the same analysis, split it into two notebooks or hand it off explicitly rather than editing in parallel.
6. **Python environment.** Use a Python 3.14 kernel with the project's dependencies on the selected local or remote environment. For a local session, run `uv python install 3.14`, `uv sync`, and `uv run jupyter lab notebooks/` from the repository root. The "Open in Colab" badges remain, but a hosted kernel using another Python version cannot run this project. Each notebook checks the kernel version before importing project dependencies. Follow rule 3 when choosing where and whether to execute.
